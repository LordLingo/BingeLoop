# BingeLoop

A mobile-first web app (brand name: BingeLoop) where users log TV shows and movies, rate them 1–5 stars, leave a comment, and tag a category (Drama, Comedy, Thriller, etc.).

## Run & Operate

- `pnpm --filter @workspace/api-server run dev` — run the API server (port 5000)
- `pnpm run typecheck` — full typecheck across all packages
- `pnpm run build` — typecheck + build all packages
- `pnpm --filter @workspace/api-spec run codegen` — regenerate API hooks and Zod schemas from the OpenAPI spec
- `pnpm --filter @workspace/db run push` — push DB schema changes (dev only)
- Required env: `DATABASE_URL` — Postgres connection string

## Stack

- pnpm workspaces, Node.js 24, TypeScript 5.9
- API: Express 5
- DB: PostgreSQL + Drizzle ORM
- Validation: Zod (`zod/v4`), `drizzle-zod`
- API codegen: Orval (from OpenAPI spec)
- Build: esbuild (CJS bundle)

## Where things live

- Frontend: `artifacts/watchlist/` (React + Vite, served at `/`)
- API contract (source of truth): `lib/api-spec/openapi.yaml`
- DB schema: `lib/db/src/schema/` (`entries.ts`, `userActivity.ts`, `watchlist.ts`, `approvals.ts`)
- API routes: `artifacts/api-server/src/routes/` (`entries.ts`, `activity.ts`, `watchlist.ts`, `approvals.ts`); shared auth in `middlewares/requireAuth.ts`
- Generated hooks: `@workspace/api-client-react`; generated Zod: `@workspace/api-zod`

## Architecture decisions

- Categories are a server-defined canonical list (`CATEGORIES` in `entries.ts`), exposed via `GET /categories` and enforced on create/update. To add a category, edit that array.
- On create, `comment` is an optional string (null is rejected); on update, `comment` is nullable so it can be cleared.
- `/stats` aggregates in the handler (totals, avg rating, per-category counts) rather than via SQL aggregation, for simplicity at this scale.
- Auth is Replit-managed Clerk (email/password, cookie-based on web). `requireAuth` is mounted on the entries router, so `/entries`, `/stats`, `/categories` all require a session; `/healthz` stays public.
- Named groups (NOT a single global group): `groups` (`id, name, ownerId, createdAt`) + `group_members` (`groupId, userId, displayName, role, joinedAt`, `unique(groupId, userId)`). Users create+name groups, belong to MULTIPLE, and switch an ACTIVE group client-side (`active-group-context`, localStorage-persisted, validated against `useListGroups`). Groups start EMPTY — there is NO migration of pre-existing data. Routes: `POST/GET /groups`, `GET/PATCH /groups/{id}`, `POST /groups/{id}/leave`, `POST /groups/{id}/invite`. Membership helpers live in `lib/groups.ts` (`getMemberGroupIds`, `getMembership`, `isMember`, `getGroupMemberIds`, `usersShareGroup`).
- Privacy / data scoping: entries, watchlist, and approvals stay PERSONAL (each row has `userId`, NO `groupId` column). A user may see another user's data ONLY if they share ≥1 group (or it's their own). Library `GET /entries` and `GET /stats` are scoped by member set: `userId` param → that single member (requires `usersShareGroup`); `groupId` param → ALL members of that group (caller must be `isMember`, else 403); neither → caller's own only (matches the watchlist default). The web library/hero-stats always pass the active `groupId` so the stat totals match the visible cards; the caller-only default is just the safe fallback. Each entry also stores `addedBy` (display-name snapshot resolved from Clerk on create) for attribution.
- Consistent non-member `groupId` contract: ALL group-scoped reads/writes (`GET /entries`, `GET /stats`, `GET /watchlist`, and `GET/PUT/DELETE /approvals`) return a 403 (`"You are not a member of this group"`) when a `groupId` is passed for a group the caller doesn't belong to — there is NO silent fallback to caller-only/empty. The web client always sends the active `groupId` (validated against `useListGroups`), so this is an edge case (e.g. stale localStorage after leaving a group); the UI degrades gracefully because every consumer keys off `isLoading`/`!data` empty states. Membership is checked via `isMember` (entries/stats/watchlist) or the `resolveMemberIds` helper (approvals, returns `null` to signal non-membership).
- Personal watchlist: `watchlist_items` table (per-user saved shows) with `unique(userId, titleKey, mediaType)`. A "show" has no canonical entity — the same show across users is matched by `titleKey` (normalized `lower(trim(title))`) + `mediaType`. `GET /watchlist` returns the caller's saved items each annotated with `alsoEngagedBy`: display names of OTHER users who have rated (have an `entries` row) OR saved that same show, deduped by userId across both sources and caller-excluded. `POST /watchlist` is an idempotent upsert; `DELETE /watchlist/:id` is ownership-scoped (id + userId). Save/Saved toggle lives on each library card; `/watchlist` is the personal page.
- Wife-approved poll: `show_approvals` table (per-user answer per show) with `unique(userId, titleKey, mediaType)` and `approval` in (`yes`,`no`,`solo`). Same "same-show" identity as watchlist (`titleKey` = normalized `lower(trim(title))` + `mediaType`). `GET /approvals` groups counts across ALL users by `(titleKey, mediaType, approval)` and overlays the caller's own answer as `myApproval`. `PUT /approvals` upserts the caller's answer (idempotent); `DELETE /approvals?title=&mediaType=` clears it (ownership-scoped on all three columns). Both write endpoints return the fresh `ShowApproval` summary. Interactive `ApprovalControl` (tap an option to set, tap again to clear) lives on the view-entry page; read-only `ApprovalSummary` (e.g. "3 Yes / 1 No") shows on library cards and the watchlist page.
- Spicy flag: `show_spice` table — a DIRECT MIRROR of the wife-approved feature but with only two answers, `spicy` in (`yes`,`no`) (no "solo"). Same identity/scoping/contract as approvals (`unique(userId, titleKey, mediaType)`, group-scoped tallies via `resolveMemberIds`, non-member `groupId` → 403). Routes `GET/PUT/DELETE /spice` (mounted after approvals in `routes/index.ts`), returning a `ShowSpicy` summary (`titleKey, mediaType, yes, no, mySpicy`). Interactive `SpicyControl` ("Spicy? 🌶️", Yes/No, tap-again-to-clear) sits under `ApprovalControl` on the view-entry page; read-only `SpicySummary` shows "{yes} Spicy 🌶️" (only when yes>0) on library + watchlist cards. Hook `useSpiceMap`/`spiceKey` mirrors `useApprovalMap`. To extend either poll, edit both in lockstep — they are intentionally parallel.
- Threaded per-show discussion: `show_comments` table (`id, userId, authorName` snapshot, `titleKey, mediaType, parentId` nullable self-FK with `onDelete cascade`, `body, createdAt`, index on `(titleKey, mediaType)`). Same "same-show" identity as approvals/spice (`titleKey` = normalized `lower(trim(title))` + `mediaType`) and the SAME group-scoping contract (`resolveMemberIds(callerId, groupId)` → `[callerId]` with no group, all member ids if member, `null` → 403; check runs BEFORE any insert). Routes `GET/POST /comments` (mounted after spice in `routes/index.ts`). `GET` returns the FLAT list of comments authored by the resolved member set for a show, oldest first (clients nest by `parentId`); without a `groupId` only the caller's own comments. `POST` requires membership, resolves `authorName` via `resolveDisplayName` (like entry `addedBy`), and for a reply validates the `parentId` exists, is on the SAME show, AND is authored by a member of the resolved set (else 400). The created comment is returned with `201` and parsed with `ListCommentsResponseItem` (Orval emits no zod `Response` schema for 201s — see memory). Frontend `CommentThread` (`title`, `mediaType`, active `groupId`) renders under the Thoughts block on the view-entry page: a top-level composer plus per-comment inline Reply, nesting replies recursively (`border-l` indent); styled like `ApprovalControl`/`SpicyControl` (`rounded-2xl border border-border bg-card`). No edit/delete (out of scope).
- Activity feed: `GET /activity/feed` (in `routes/activity.ts`, params `groupId`+`limit` default 50/max 100) returns a reverse-chronological combined feed of member actions across FIVE existing sources (no new table): entries→`rating`, watchlist_items→`watchlist`, show_comments→`comment`, show_approvals→`approval`, show_spice→`spice`. Same group-scoping contract as the polls (local `resolveMemberIds(callerId, groupId)` → `[callerId]` with no group, all member ids if member, `null`→403; 403 runs before any source query). Comment/approval/spice rows store only normalized `titleKey`, so the handler builds `titleByKey`+`entryIdByKey` maps from the members' entries (ordered `asc(createdAt)` so newest entry/title wins) with watchlist backfilling titles only; each non-entry event inherits that display title + a linkable `entryId` (null if no entry exists for the show). Approval/spice rows store only `userId` → actor name resolved via the `group_members.displayName` map (with `resolveDisplayName` fallback for the no-group caller). Each `ActivityItem` has a composite string `id` (`"rating:123"` etc.), `type`, `actorName`, `title`, `mediaType`, `createdAt`, plus type-specific `entryId`/`rating`/`approval`/`spicy` (all nullable). Frontend `/activity` page (`pages/activity.tsx`, linked from the home header next to My Watchlist) always passes the active `groupId`, renders title as a `/entry/:id` Link only when `entryId != null`, shows `StarRating` for ratings, and uses `formatDistanceToNow` for relative time.
- New-activity badge: `user_activity` table stores per-user `lastSeenAt`. `POST /activity/check-in` reads the prior `lastSeenAt`, counts entries created since then by OTHER users (excludes the caller's own), updates `lastSeenAt` to now, and returns `{ newCount, since }`. The web client calls it once on library mount and shows a dismissible badge when `newCount > 0`. First visit returns 0 (no prior timestamp).
- Invite links (group-scoped): `invites` table is ONE reusable invite PER GROUP (`unique(groupId)`, high-entropy random `token` via `randomBytes(16).base64url`, plus `createdBy`/`createdByName`); there is NO `invite_acceptances` table — joining writes a `group_members` row directly. `POST /groups/{id}/invite` (auth, caller must be a member) is create-or-get for that group's invite; `GET /invites/:token` is PUBLIC (landing page preview) and returns `{ token, groupName, inviterName, valid }` (valid=false for unknown tokens); `POST /invites/:token/accept` (auth) idempotently adds the caller to the group and returns `{ joined, groupId, groupName }` (already-a-member is a no-op with `joined=false`). Web flow: `InviteDialog` (header) generates the active group's link via `useCreateOrGetGroupInvite`; `/invite/:token` stores the token in `localStorage` and shows sign-up/sign-in CTAs; a global `InviteAccepter` (reactive on `useUser` + location) calls accept once a pending token + signed-in user coincide, then sets that group as active and invalidates the groups query.

## Product

Users create and name their own groups, invite others by link, belong to multiple groups, and switch the active group (new accounts with no groups land on an Onboarding screen to create their first). The library, hero stats, and "also engaged by" attribution are all scoped to the active group's members. Within that scope users browse their watch library with category/media-type filters and sorting, see summary stats (total logged, average rating, movie/TV split, category breakdown), and add/edit/delete entries — each with a title, movie/TV type, 1–5 star rating, category, and optional comment. Entries, watchlist saves, and approvals remain personal to each user; you only see another member's data when you share a group with them.

## Design

- Light "cinematic editorial" theme: pure white (`#FFFFFF`) page background with near-black (`#111111` ≈ `hsl(0 0% 7%)`) page-level text (logo wordmark, headings, stat numbers, filter buttons). Warm gold accent (`#E8B500` ≈ `hsl(46 100% 45%)`) is kept as `--primary`/`--accent`/`--ring` for the gold star ratings, the logo film/brand icon, the `+` FAB, and other small accents — gold is an ACCENT only, never large text on white (gold-on-white fails contrast). Logo wordmarks are `text-foreground` (black) with a `text-primary` (gold) icon.
- Fonts (loaded in `index.html` + `index.css`): `Bebas Neue` as the display font (`--font-serif`, used for all headings/logo via the base `h1–h6` rule — set in uppercase with wide tracking for a movie-poster feel); `Oswald` as body (`--font-sans`).
- `:root` and `.dark` tokens are kept IDENTICAL (both hold the LIGHT palette) and `<html class="dark">` is still set (so Clerk's shadcn theme + any `dark:` utilities stay consistent). Editing the palette means editing BOTH blocks in `index.css`. Clerk's own `appearance.variables` in `App.tsx` are an independent light palette.
- Show cards are a NAVY gradient surface (`#1E3A5F → #142841`) via `.poster-card`, which ALSO re-scopes the design tokens locally (`--foreground`/`--card-foreground` → white, `--muted-foreground` → light cool gray, `--background`/`--muted`/`--border`/`--input` → navy tones, `--badge-outline`/`--button-outline` → translucent white). This means every card-internal element that uses token-based utilities (`text-foreground`, `text-muted-foreground`, `bg-background`, `border-border`, badges, the Save button, ApprovalSummary, dividers) automatically renders readable light-on-navy with NO per-component overrides. To restyle card internals, prefer adjusting the scoped tokens on `.poster-card` over editing each card.
- `.cinematic-panel` is a subtle light gradient (`hsl(0 0% 97%) → background`) for page hero sections; hero stat sub-cards use `bg-black/[0.03]` + `border-black/10` (faint on white). Avoid large `bg-primary` (gold) fills as backgrounds.

## Gotchas

- API auth depends on router MOUNT ORDER. `entriesRouter` calls `router.use(requireAuth)` with no path, and every sub-router in `routes/index.ts` is mounted via `router.use(...)` with no path prefix — so that global auth runs for EVERY request that reaches `entriesRouter` and 401s anything still unhandled. Any PUBLIC route (e.g. `GET /invites/:token`) MUST be mounted before `entriesRouter`; `healthRouter` and `invitesRouter` are intentionally mounted first. Do not reorder routers without preserving this.

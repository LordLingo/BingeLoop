# Architecture — core decisions

Cross-cutting decisions that the feature docs build on. For per-feature detail see [features.md](./features.md).

## Entries, categories, stats, auth

- Categories are a server-defined canonical list (`CATEGORIES` in `entries.ts`), exposed via `GET /categories` and enforced on create/update. To add a category, edit that array.
- On create, `comment` is an optional string (null is rejected); on update, `comment` is nullable so it can be cleared.
- `/stats` aggregates in the handler (totals, avg rating, per-category counts) rather than via SQL aggregation, for simplicity at this scale.
- Auth is Replit-managed Clerk (email/password, cookie-based on web). `requireAuth` is mounted on the entries router, so `/entries`, `/stats`, `/categories` all require a session; `/healthz` stays public.

## Groups & membership

- Named groups (NOT a single global group): `groups` (`id, name, ownerId, createdAt`) + `group_members` (`groupId, userId, displayName, role, status, joinedAt`, `unique(groupId, userId)`). Users create+name groups, belong to MULTIPLE, and switch an ACTIVE group client-side (`active-group-context`, localStorage-persisted, validated against `useListGroups`). Groups start EMPTY — there is NO migration of pre-existing data. Routes: `POST/GET /groups`, `GET/PATCH /groups/{id}`, `POST /groups/{id}/leave`, `DELETE /groups/{id}/members/{userId}`, `POST /groups/{id}/invite`. Membership helpers live in `lib/groups.ts` (`getMemberGroupIds`, `getMembership`, `isMember`, `getGroupMemberIds`, `usersShareGroup`).
- Owner removes member (soft-removal): `group_members.status` is `active` (default) or `removed`. The split is intentional — ACCESS helpers count only ACTIVE rows (`getMemberGroupIds`, `getMembership`, `isMember` all filter `status="active"`), while the CONTENT-set helper `getGroupMemberIds` returns ALL rows (incl. `removed`). So removing a member revokes their access (they can't list/read/switch to the group, and every group-scoped read/write 403s for them) but their contributed content (entries/ratings, comments, watchlist, Top Four, lists, audience/spice picks — all personal `userId` rows) stays visible to the rest of the group under their original `displayName`/`addedBy` snapshot. `usersShareGroup(caller, target)` is ASYMMETRIC by design: caller must be ACTIVE in a shared group, target may be active OR removed — lets active members open a removed contributor's `/member/:id`, while a removed caller (no active membership) loses cross-user visibility. `DELETE /groups/{id}/members/{userId}` is OWNER-ONLY (403 otherwise), 400 if owner targets self, 404 if target isn't an active member; it sets `status="removed"` (keeps the row + snapshot). GET `/groups` & `/groups/{id}` list/count only ACTIVE members. Rejoin via invite REACTIVATES the existing `removed` row (`status="active"`) instead of inserting (would violate `unique(groupId,userId)`). The leave route's "remaining members" / ownership-transfer logic also filters ACTIVE, and tears down leftover `removed` rows when the last active member leaves. Frontend: owner sees a per-member trash button (hidden for self) in the `group.tsx` Members list, gated behind an `AlertDialog` confirmation.

## Privacy / data scoping

- Entries, watchlist, and audience picks stay PERSONAL (each row has `userId`, NO `groupId` column). A user may see another user's data ONLY if they share ≥1 group (or it's their own). Library `GET /entries` and `GET /stats` are scoped by member set: `userId` param → that single member (requires `usersShareGroup`); `groupId` param → ALL members of that group (caller must be `isMember`, else 403); neither → caller's own only (matches the watchlist default). The web library/hero-stats always pass the active `groupId` so the stat totals match the visible cards; the caller-only default is just the safe fallback. Each entry also stores `addedBy` (display-name snapshot resolved via `resolveDisplayName` on create) for attribution; the Entry API response also exposes `addedById` (the entry's `userId`, mapped via the `withAddedById` helper in `routes/entries.ts` across list/get/create/update) so the UI can link attribution to that member's profile. On library cards the attribution is a tappable "Added by {name}" control (gold/`text-primary` username) that navigates to `/member/{addedById}`.
- Consistent non-member `groupId` contract: ALL group-scoped reads/writes (`GET /entries`, `GET /stats`, `GET /watchlist`, and `GET/PUT/DELETE /audiences`) return a 403 (`"You are not a member of this group"`) when a `groupId` is passed for a group the caller doesn't belong to — there is NO silent fallback to caller-only/empty. The web client always sends the active `groupId` (validated against `useListGroups`), so this is an edge case (e.g. stale localStorage after leaving a group); the UI degrades gracefully because every consumer keys off `isLoading`/`!data` empty states. Membership is checked via `isMember` (entries/stats/watchlist) or the `resolveMemberIds` helper (audiences, returns `null` to signal non-membership).
